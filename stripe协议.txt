<h2 id="前言">前言</h2>
<p>做过 SaaS 订阅的人都知道，Stripe 是全球最主流的支付处理商。几乎所有主流 AI 平台——从对话类到图像类——都用 Stripe 处理信用卡支付。</p>
<p>但很少有人去研究 Stripe Checkout 背后的协议细节。大多数人的认知停留在&quot;调一下 API、跳个 Checkout 页面、信用卡扣完款就行了&quot;。</p>
<p>实际上，Stripe 的 Checkout Session 协议远比你想象的复杂。从 <code>checkout_ui_mode</code> 的 <code>custom</code> 与 <code>hosted</code> 两种模式，到 <code>ConfirmationToken</code> 的创建机制，再到 <code>PaymentIntent</code> 的 <code>requires_action</code> 状态下 3DS 验证挑战的处理——每一步都有大量的协议细节、反欺诈检测和时序要求。</p>
<p>今天我把这些全拆开。从 HAR 抓包出发，逐层剖析 Stripe 协议支付的完整链路，并提供 5 套不同技术栈的实现源码。</p>
<hr />
<h2 id="零、方法论：如何逆向-Stripe-支付协议">零、方法论：如何逆向 Stripe 支付协议</h2>
<p>在开始之前，先讲方法论。所有协议支付的起点都是 <strong>HAR 抓包</strong>。</p>
<h3 id="0-1-什么是-HAR-文件">0.1 什么是 HAR 文件</h3>
<p>HAR（HTTP Archive）是浏览器开发者工具导出的完整 HTTP 交互记录。包含每个请求的 URL、Headers、Body、Response，以及精确的时序信息。</p>
<p>打开 Chrome DevTools → Network → 完成一次真实支付 → 右键 → Save all as HAR with content。</p>
<p><strong>这个 HAR 文件就是你的 ground truth</strong>。所有协议支付的字段、值、顺序、编码方式，都以 HAR 为准。代码实现、第三方文档、安全审计报告——全部都可能过时或有误，只有 HAR 是当时浏览器真实发出的请求。</p>
<h3 id="0-2-HAR-分析流程">0.2 HAR 分析流程</h3>
<ol>
<li><strong>筛选关键域名</strong>：<code>api.stripe.com</code>、<code>m.stripe.com</code>、<code>checkout.stripe.com</code>、平台 API 域名</li>
<li><strong>按时间排序</strong>：找出完整的请求链路</li>
<li><strong>对比成功和失败</strong>：同一流程的成功 HAR 和失败 HAR，diff 出关键差异</li>
<li><strong>提取稳定字段</strong>：跨多个 HAR 都一致的值可以硬编码</li>
<li><strong>标记动态字段</strong>：每次不同的值（Session ID、Token、时间戳）需要运行时获取</li>
</ol>

<p>通过分析多个成功支付的 HAR 文件，提取出标准的浏览器 Checkout 请求序列：</p>

<hr />
<h2 id="一、为什么要做-协议支付">一、为什么要做&quot;协议支付&quot;</h2>
<p>先搞清楚一个概念：什么是协议支付（Protocol Payment）？</p>
<p><strong>浏览器支付</strong>：用户打开 Stripe Checkout 页面 → 手动填写信用卡号 → 点击支付 → 完成。这是正常流程。</p>
<p><strong>协议支付</strong>：用纯 HTTP API 请求模拟浏览器的完整操作链路，包括 Stripe 的内部 API（不是官方 SDK 暴露的那些），直接在协议层完成支付，不需要浏览器。</p>
<p>为什么要这么做？</p>
<ol>
<li><strong>自动化需求</strong>：批量管理订阅时，手动操作不现实</li>
<li><strong>性能需求</strong>：浏览器（Puppeteer/Playwright）启动慢、占内存大、不稳定；协议支付 &lt;5s 完成</li>
<li><strong>环境隔离</strong>：服务端运行，不需要 GUI 环境</li>
<li><strong>学习价值</strong>：深入理解支付系统的工作原理</li>
</ol>
<hr />
<h2 id="二、Stripe-Checkout-Session-的两种模式">二、Stripe Checkout Session 的两种模式</h2>
<p>Stripe Checkout 有两种 <code>checkout_ui_mode</code>，这是整个协议支付的第一个分叉点：</p>
<h3 id="2-1-Custom-模式-oaics-前缀">2.1 Custom 模式 (<code>oaics_</code> 前缀)</h3>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br></pre></td><td class="code"><pre><span class="line">POST /payments/checkout</span><br><span class="line">&#123;</span><br><span class="line">  &quot;checkout_ui_mode&quot;: &quot;custom&quot;,</span><br><span class="line">  &quot;currency&quot;: &quot;PHP&quot;,</span><br><span class="line">  &quot;plan_type&quot;: &quot;plus&quot;</span><br><span class="line">&#125;</span><br><span class="line">→ &#123;&quot;checkout_session_id&quot;: &quot;oaics_xxx&quot;, &quot;stripe_publishable_key&quot;: &quot;pk_live_...&quot;&#125;</span><br></pre></td></tr></table></figure>
<p>Custom 模式返回的 Session ID 以 <code>oaics_</code> 开头。这种模式下：</p>
<ul>
<li>前端需要自己挂载 Stripe Elements</li>
<li>通过 Stripe.js 创建 <code>ConfirmationToken</code></li>
<li>调用平台的 <code>confirm</code> 接口完成支付</li>
<li><strong>直接</strong>在 Stripe API 上确认 PaymentIntent</li>
</ul>
<h3 id="2-2-Hosted-模式-cs-live-前缀">2.2 Hosted 模式 (<code>cs_live_</code> 前缀)</h3>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br></pre></td><td class="code"><pre><span class="line">POST /payments/checkout</span><br><span class="line">&#123;</span><br><span class="line">  &quot;checkout_ui_mode&quot;: &quot;hosted&quot;,</span><br><span class="line">  &quot;currency&quot;: &quot;PHP&quot;,</span><br><span class="line">  &quot;plan_type&quot;: &quot;plus&quot;</span><br><span class="line">&#125;</span><br><span class="line">→ &#123;&quot;checkout_session_id&quot;: &quot;cs_live_xxx&quot;, &quot;url&quot;: &quot;https://checkout.stripe.com/...&quot;&#125;</span><br></pre></td></tr></table></figure>
<p>Hosted 模式返回 <code>cs_live_</code> 前缀的 Session。这种模式下：</p>
<ul>
<li>Stripe 托管整个 Checkout 页面</li>
<li>走 Stripe Payment Page 的内部协议</li>
<li>流程更复杂，涉及 <code>ppage_</code> 初始化、<code>elements</code> Session、<code>inline_confirm</code></li>
<li>需要额外处理平台侧的 <code>approve</code> 操作</li>
</ul>
<p>两种模式的选择取决于平台的 billing 配置和你的需求。一般来说：</p>
<ul>
<li>如果平台的计费货币与你的信用卡货币一致 → Custom 模式更简单</li>
<li>如果存在货币不匹配（比如用美元卡付菲律宾比索订阅）→ 可能只有 Hosted 模式可用</li>
</ul>
<h3 id="2-3-决定性参数：checkout-ui-mode">2.3 决定性参数：<code>checkout_ui_mode</code></h3>
<p>通过大量测试验证，<strong>决定返回 <code>oaics_</code> 还是 <code>cs_live_</code> 的唯一参数就是 <code>checkout_ui_mode</code></strong>。</p>

<h2 id="三、Custom-模式协议流程详解">三、Custom 模式协议流程详解</h2>
<p>Custom 模式是最干净的协议支付路径。完整流程 8 步：</p>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br></pre></td><td class="code"><pre><span class="line">┌──────────────────────────────────────┐</span><br><span class="line">│ 1. 刷新 Session（获取最新 Token）      │</span><br><span class="line">│ 2. 查询账号信息（确认当前订阅状态）     │</span><br><span class="line">│ 3. 获取定价信息（币种+金额）           │</span><br><span class="line">│ 4. 创建 Checkout Session              │</span><br><span class="line">│ 5. 更新税务信息（Billing 地址）        │</span><br><span class="line">│ 6. 创建 ConfirmationToken（卡号→Token）│</span><br><span class="line">│ 7. 确认支付（Confirm Checkout）        │</span><br><span class="line">│ 8. 确认 PaymentIntent（Stripe 侧）     │</span><br><span class="line">└──────────────────────────────────────┘</span><br></pre></td></tr></table></figure>
<h3 id="3-1-创建-ConfirmationToken">3.1 创建 ConfirmationToken</h3>
<p>这是协议支付最核心的一步。浏览器里，Stripe.js 会在 iframe 中收集卡号，然后调用 Stripe 的内部 API 创建一个 <code>ConfirmationToken</code>（<code>ctoken_</code> 前缀）。</p>
<p>协议支付需要直接模拟这个请求：</p>
<figure class="highlight http"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br></pre></td><td class="code"><pre><span class="line">POST https://api.stripe.com/v1/confirmation_tokens</span><br><span class="line"><span class="attribute">Content-Type</span><span class="punctuation">: </span>application/x-www-form-urlencoded</span><br><span class="line"></span><br><span class="line">type=card</span><br><span class="line">&amp;payment_method_data[type]=card</span><br><span class="line">&amp;payment_method_data[card][number]=4242424242424242</span><br><span class="line">&amp;payment_method_data[card][exp_month]=12</span><br><span class="line">&amp;payment_method_data[card][exp_year]=2029</span><br><span class="line">&amp;payment_method_data[card][cvc]=123</span><br><span class="line">&amp;payment_method_data[billing_details][name]=John Doe</span><br><span class="line">&amp;payment_method_data[billing_details][address][country]=US</span><br><span class="line">&amp;payment_method_data[billing_details][address][postal_code]=97201</span><br><span class="line">&amp;key=pk_live_xxx</span><br><span class="line">&amp;_stripe_version=2025-03-31.basil</span><br></pre></td></tr></table></figure>
<p>几个关键细节：</p>
<ol>
<li><strong><code>key</code> 必须是平台的 Stripe Publishable Key</strong>，不是你自己的</li>
<li><strong><code>_stripe_version</code> 必须匹配</strong>当前 Stripe.js 的 API 版本</li>
<li><strong>需要传 Stripe.js 的指纹参数</strong>：<code>guid</code>、<code>muid</code>、<code>sid</code>、<code>time_on_page</code></li>
<li><strong>Referer 必须是平台域名</strong>，Stripe 会校验</li>
</ol>
<h4 id="卡号格式细节">卡号格式细节</h4>
<p>HAR 验证发现，浏览器发送的卡号<strong>带空格</strong>（<code>4004 1641 0185 9397</code>），而不是纯数字。不过 Stripe 接受两种格式。</p>
<h4 id="guid-muid-sid-格式">guid/muid/sid 格式</h4>
<p>这三个指纹 ID 的格式比很多人以为的更复杂。HAR 验证的正确格式是 <strong>42 字符</strong>：</p>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br></pre></td><td class="code"><pre><span class="line">guid = randomUUID() + randomHex(6)</span><br><span class="line">     = xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx + 6位hex</span><br><span class="line">     = 36字符UUID + 6字符 = 42字符</span><br></pre></td></tr></table></figure>
<p>例如：<code>a1b2c3d4-e5f6-4789-abcd-ef0123456789abc123</code></p>
<p>有些实现用 32 位纯 hex 也能工作，但 HAR 中浏览器发送的是 42 字符格式。</p>
<h4 id="Attribution-元数据（两层结构）">Attribution 元数据（两层结构）</h4>
<p><code>confirmation_tokens</code> 请求中有一组 <code>client_attribution_metadata</code> 字段，这些是 Stripe 用来追踪支付集成来源的元数据：</p>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br></pre></td><td class="code"><pre><span class="line">payment_user_agent = stripe.js/...</span><br><span class="line">client_session_id = &lt;UUID&gt;                           # 每 session 唯一</span><br><span class="line">merchant_integration_source = elements               # ← oaics_ 固定 &quot;elements&quot;</span><br><span class="line">merchant_integration_version = 2021</span><br><span class="line">merchant_integration_subtype = payment-element</span><br><span class="line">payment_intent_creation_flow = deferred</span><br><span class="line">payment_method_selection_flow = merchant_specified    # ← oaics_ 固定</span><br><span class="line">additional_elements = [expressCheckout, payment, address]</span><br></pre></td></tr></table></figure>
<p>这些字段在 <code>confirmation_tokens</code> 请求中出现两次——一次在 <code>payment_method_data</code> 内部，一次在顶层。<strong>两层的值大部分相同，但 <code>merchant_integration_source</code> 在 confirm 请求中变成 <code>l1</code></strong>。这个细节从 HAR 中才能发现。</p>

<h3 id="3-2-确认-Checkout">3.2 确认 Checkout</h3>
<p>拿到 <code>ConfirmationToken</code> 后，调用平台的 confirm 接口：</p>
<figure class="highlight http"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br></pre></td><td class="code"><pre><span class="line">POST /api/v1/payments/checkout/confirm</span><br><span class="line">&#123;</span><br><span class="line">  &quot;checkout_session_id&quot;: &quot;oaics_xxx&quot;,</span><br><span class="line">  &quot;confirmation_token&quot;: &quot;ctoken_1xxx&quot;</span><br><span class="line">&#125;</span><br></pre></td></tr></table></figure>
<p>这一步平台会拿着你的 token 去 Stripe 创建 PaymentIntent 并尝试扣款。</p>
<p>如果一切顺利（卡余额充足、无 3DS 要求），PaymentIntent 直接变成 <code>succeeded</code>，订阅激活。</p>
<p>如果遇到 3DS 验证，流程会更复杂——我们在第五节讲。</p>
<h3 id="3-3-Elements-Session-—-获取支付配置">3.3 Elements Session — 获取支付配置</h3>
<p>在创建 ConfirmationToken 之前，需要先调用 Stripe 的 <code>elements/sessions</code> API 获取支付配置信息。这一步在 HAR 中被调用<strong>两次</strong>——一次在税务更新前，一次在税务更新后。</p>
<figure class="highlight http"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br></pre></td><td class="code"><pre><span class="line">GET https://api.stripe.com/v1/elements/sessions?deferred_intent[mode]=subscription</span><br><span class="line">    &amp;deferred_intent[amount]=98214</span><br><span class="line">    &amp;deferred_intent[currency]=php</span><br><span class="line">    &amp;deferred_intent[setup_future_usage]=off_session</span><br><span class="line">    &amp;deferred_intent[payment_method_types][0]=card</span><br><span class="line">    &amp;type=deferred_intent</span><br><span class="line">    &amp;key=pk_live_xxx</span><br><span class="line">    &amp;_stripe_version=2025-03-31.basil</span><br></pre></td></tr></table></figure>
<p>关键返回值：</p>
<ul>
<li><strong><code>elements_session_id</code></strong>：<code>elements_session_xxx</code>，后续 confirm 请求需要</li>
<li><strong><code>customer_session_client_secret</code></strong>：<code>cuss_xxx</code>，客户会话密钥</li>
<li><strong><code>payment_method_configuration</code></strong>：<code>pmc_xxx</code>，支付方式配置 ID</li>
</ul>
<h3 id="3-4-税务地址优化-—-US-免税地址消除-VAT">3.4 税务地址优化 — US 免税地址消除 VAT</h3>
<p>这是一个实际操作中极其重要的技巧。</p>
<p>很多 SaaS 平台默认按账号注册地收税。比如菲律宾区的订阅，标价 ₱982.14 但实际会加 12% VAT 变成 ₱1,100+。</p>
<p><strong>解决方案</strong>：在 <code>taxes</code> API 调用中使用美国免税州地址。</p>
<figure class="highlight http"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br></pre></td><td class="code"><pre><span class="line">POST /api/v1/payments/checkout/taxes</span><br><span class="line">&#123;</span><br><span class="line">  &quot;checkout_session_id&quot;: &quot;oaics_xxx&quot;,</span><br><span class="line">  &quot;billing_details&quot;: &#123;</span><br><span class="line">    &quot;name&quot;: &quot;John Doe&quot;,</span><br><span class="line">    &quot;address&quot;: &#123;</span><br><span class="line">      &quot;country&quot;: &quot;US&quot;,</span><br><span class="line">      &quot;state&quot;: &quot;OR&quot;,</span><br><span class="line">      &quot;city&quot;: &quot;Portland&quot;,</span><br><span class="line">      &quot;postal_code&quot;: &quot;97201&quot;,</span><br><span class="line">      &quot;line1&quot;: &quot;123 Main St&quot;</span><br><span class="line">    &#125;</span><br><span class="line">  &#125;</span><br><span class="line">&#125;</span><br></pre></td></tr></table></figure>
<p>美国有 5 个无销售税的州：</p>
<ul>
<li><strong>Oregon (OR)</strong> — 无销售税</li>
<li><strong>Montana (MT)</strong> — 无销售税</li>
<li><strong>Delaware (DE)</strong> — 无销售税</li>
<li><strong>New Hampshire (NH)</strong> — 无销售税</li>
<li><strong>Alaska (AK)</strong> — 大部分地区无销售税</li>
</ul>
<p>HAR 验证：使用 US 地址后 tax=0，最终金额保持 ₱982.14。</p>
<p><strong>重要</strong>：<code>taxes</code> 和后续 <code>confirmation_tokens</code> 中的地址必须一致。同一个 session 内选择一个地址后全程复用。</p>
<h3 id="3-5-PaymentIntent-确认-—-Stripe-侧扣款">3.5 PaymentIntent 确认 — Stripe 侧扣款</h3>
<p>平台的 <code>/confirm</code> 返回 <code>client_secret</code>（格式：<code>pi_xxx_secret_xxx</code>）后，需要调用 Stripe 的 <code>payment_intents/confirm</code> 完成实际扣款：</p>
<figure class="highlight http"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br></pre></td><td class="code"><pre><span class="line">POST https://api.stripe.com/v1/payment_intents/&#123;pi_id&#125;/confirm</span><br><span class="line"></span><br><span class="line">return_url = https://platform.example.com/checkout/verify?stripe_session_id=oaics_xxx</span><br><span class="line">confirmation_token = ctoken_xxx</span><br><span class="line">key = pk_live_xxx</span><br><span class="line">_stripe_version = 2025-03-31.basil</span><br><span class="line">client_secret = pi_xxx_secret_xxx</span><br><span class="line">client_attribution_metadata[client_session_id] = &lt;UUID&gt;</span><br><span class="line">client_attribution_metadata[merchant_integration_source] = l1</span><br></pre></td></tr></table></figure>
<p>注意这里 <code>merchant_integration_source</code> 变成了 <code>l1</code>，不再是 <code>elements</code>。</p>
<h4 id="PI-拒卡重试">PI 拒卡重试</h4>
<p>HAR 验证了一个重要特性：<strong>同一个 PaymentIntent 被拒卡后可以用新的 ConfirmationToken 重试</strong>。</p>
<p>流程：</p>
<ol>
<li>第一张卡 → <code>generic_decline</code> → PI 状态 <code>requires_payment_method</code></li>
<li>创建新的 <code>confirmation_token</code>（用另一张卡）</li>
<li>再次调用 <code>payment_intents/confirm</code></li>
<li>第二张卡 → <code>succeeded</code></li>
</ol>
<p><strong>这意味着拒卡不需要重建整个 Checkout Session</strong>，只需要换卡重建 token。</p>
<h3 id="3-6-Cookie-隔离架构">3.6 Cookie 隔离架构</h3>
<p>协议支付需要严格的 Cookie 隔离。一个常见的 bug 是平台的 Cookie 被发送到 Stripe API，或反过来。</p>
<p>最佳实践：使用两个独立的 HTTP 客户端：</p>
<figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br></pre></td><td class="code"><pre><span class="line"><span class="comment"># 平台客户端 — 带 Cookie（session token）</span></span><br><span class="line">platform_http = HttpClient(cookies_enabled=<span class="literal">True</span>)</span><br><span class="line">platform_http.set_cookie(<span class="string">&quot;__Secure-platform-auth&quot;</span>, session_token)</span><br><span class="line"></span><br><span class="line"><span class="comment"># Stripe 客户端 — 不带 Cookie</span></span><br><span class="line">stripe_http = HttpClient(cookies_enabled=<span class="literal">False</span>)</span><br></pre></td></tr></table></figure>
<p><strong>绝不</strong>让 Stripe 客户端发送平台 Cookie，也不要让平台客户端发送 Stripe 的 Cookie。</p>

<p>关键差异：</p>
<ul>
<li>需要传 <code>checkout_session_id</code>（Custom 模式不需要）</li>
<li><code>elements_init_source</code> 是 <code>custom_checkout</code>（不是 <code>elements</code>）</li>
<li>需要传 <code>referrer_host</code>、<code>stripe_js_id</code>、<code>locale</code></li>

</ul>
<p>返回值中有一个重要字段 <code>passive_captcha.rqdata</code>——这是 hCaptcha Enterprise 的 <code>rqdata</code>，后续 confirm 如果触发 challenge 需要用到。</p>
<h3 id="4-3-Hosted-模式的-Confirm-请求">4.3 Hosted 模式的 Confirm 请求</h3>

<p>这个请求的 body 字段比 Custom 模式多很多：</p>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span><br><span class="line">16</span><br></pre></td><td class="code"><pre><span class="line">elements_session_client[client_betas][0] = custom_checkout_server_updates_1</span><br><span class="line">elements_session_client[client_betas][1] = custom_checkout_manual_approval_1</span><br><span class="line">elements_session_client[elements_init_source] = custom_checkout</span><br><span class="line">elements_session_client[referrer_host] = platform.example.com</span><br><span class="line">elements_session_client[session_id] = elements_session_xxx</span><br><span class="line">elements_session_client[stripe_js_id] = &lt;UUID&gt;</span><br><span class="line">elements_session_client[locale] = zh</span><br><span class="line">elements_session_client[is_aggregation_expected] = false</span><br><span class="line">elements_options_client[saved_payment_method][enable_save] = auto</span><br><span class="line">elements_options_client[saved_payment_method][enable_redisplay] = auto</span><br><span class="line">init_checksum = &lt;checksum&gt;</span><br><span class="line">js_checksum = &lt;checksum&gt;</span><br><span class="line">rv_timestamp = &lt;timestamp&gt;</span><br><span class="line">expected_amount = 98214</span><br><span class="line">expected_payment_method_type = card</span><br><span class="line">version = &lt;build_hash&gt;</span><br></pre></td></tr></table></figure>

<h3 id="4-4-Approve-机制与-Sentinel-Token">4.4 Approve 机制与 Sentinel Token</h3>
<p>Hosted 模式下，<code>payment_pages/confirm</code> 成功后，状态不会直接变成 <code>succeeded</code>，而是进入 <code>requires_approval</code>（HAR 中 confirm 返回 <code>status=open</code>）。这时需要调用平台的 approve 接口：</p>
<figure class="highlight http"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br></pre></td><td class="code"><pre><span class="line">POST /api/v1/payments/checkout/approve</span><br><span class="line"><span class="attribute">Authorization</span><span class="punctuation">: </span>Bearer &#123;access_token&#125;</span><br><span class="line"><span class="attribute">X-Vendor-Challenge-Token</span><span class="punctuation">: </span>&#123;sentinel_token&#125;</span><br></pre></td></tr></table></figure>
<h4 id="Sentinel-Token-结构">Sentinel Token 结构</h4>
<p>这里的 <code>challenge_token</code> 是一个编码后的 JSON 对象，内部包含多个通过算力证明（PoW）和 Turnstile 验证生成的字段：</p>
<figure class="highlight json"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br></pre></td><td class="code"><pre><span class="line"><span class="punctuation">&#123;</span></span><br><span class="line">  <span class="attr">&quot;p&quot;</span><span class="punctuation">:</span> <span class="string">&quot;gAAAAAB...&quot;</span><span class="punctuation">,</span>     <span class="comment">// 主负载（加密后的 PoW + session 信息）</span></span><br><span class="line">  <span class="attr">&quot;c&quot;</span><span class="punctuation">:</span> <span class="string">&quot;...&quot;</span><span class="punctuation">,</span>            <span class="comment">// enforcement_token（基于 FNV-1a 的算力证明结果）</span></span><br><span class="line">  <span class="attr">&quot;id&quot;</span><span class="punctuation">:</span> <span class="string">&quot;&lt;UUID&gt;&quot;</span><span class="punctuation">,</span>        <span class="comment">// 一次性标识</span></span><br><span class="line">  <span class="attr">&quot;flow&quot;</span><span class="punctuation">:</span> <span class="string">&quot;platform_checkout&quot;</span><span class="punctuation">,</span>  <span class="comment">// 标记来源流程</span></span><br><span class="line">  <span class="attr">&quot;t&quot;</span><span class="punctuation">:</span> <span class="string">&quot;&lt;turnstile_dx_token&gt;&quot;</span>  <span class="comment">// 4000+ 字符的 Turnstile 验证 token</span></span><br><span class="line"><span class="punctuation">&#125;</span></span><br></pre></td></tr></table></figure>
<p><strong><code>t</code> 字段是核心</strong>——如果为空字符串，approve 立即返回 <code>blocked</code>。它来自 Cloudflare Turnstile 的隐式挑战验证（不是肉眼可见的验证码）。</p>
<h4 id="Sentinel-Token-生成流程">Sentinel Token 生成流程</h4>
<p>完整的 Sentinel 生成需要两个组件协作：</p>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br></pre></td><td class="code"><pre><span class="line">1. 生成 requirements_token（本地 seed + difficulty &quot;0&quot;）</span><br><span class="line">2. POST sentinel.platform.com/backend-api/sentinel/req</span><br><span class="line">   → 返回 &#123;turnstile: &#123;dx: &quot;...&quot;&#125;, ...&#125;</span><br><span class="line">3. 用 server seed 生成 enforcement_token（FNV-1a 算力证明）</span><br><span class="line">4. 在 Node.js VM 中执行 Turnstile SDK（需要 jsdom 模拟 DOM 环境）</span><br><span class="line">   → 返回 turnstile token（~4388 字符）</span><br><span class="line">5. 组装 JSON → Base64 → 设为请求头</span><br></pre></td></tr></table></figure>
<p>关键点：</p>
<ul>
<li>PoW 使用 <strong>FNV-1a</strong> 哈希算法，difficulty 对 checkout 流程通常是 “0”（即几乎不需要算力）</li>
<li>Turnstile SDK 必须在<strong>真实的 DOM 环境</strong>中执行——简单的字符串拼接无法通过验证</li>
<li>实际生产中需要 Node.js + jsdom 来执行官方 Turnstile VM</li>
<li>SDK 代码需要定期更新（随平台版本迭代）</li>
</ul>
<h4 id="Approve-的正确时机">Approve 的正确时机</h4>
<p><strong>关键发现</strong>：Approve 不应该主动调用。正确的流程是 <strong>fall-through</strong>：</p>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br></pre></td><td class="code"><pre><span class="line">confirm → status=open, requires_approval</span><br><span class="line">                       ↓</span><br><span class="line">               等待 Stripe 回调</span><br><span class="line">                       ↓</span><br><span class="line">    平台自动完成 approve（不需要客户端调）</span><br><span class="line">                       ↓</span><br><span class="line">    poll payment_page → PI 出现</span><br><span class="line">                       ↓</span><br><span class="line">    可能 requires_action → verify_challenge</span><br><span class="line">                       ↓</span><br><span class="line">    poll 到 succeeded → 完成</span><br></pre></td></tr></table></figure>
<p>但某些边缘情况下（平台回调未触发），客户端需要手动 approve。此时 Sentinel token 是必须的。</p>
<ul>
<li>Approve 是<strong>一次性操作</strong>，同一 session 不可重复</li>
<li>如果 <code>t</code> 字段为空或格式错误 → 返回 <code>blocked</code> → session 作废</li>
<li>成功的 approve 返回 <code>{&quot;result&quot;:&quot;approved&quot;}</code></li>
</ul>

<h3 id="5-1-Challenge-类型">5.1 Challenge 类型</h3>
<p>Stripe 使用 hCaptcha Enterprise 作为 3DS 验证手段：</p>

<h3 id="5-2-verify-challenge-完整请求格式">5.2 verify_challenge 完整请求格式</h3>
<p>HAR 中验证的 <code>verify_challenge</code> 完整请求：</p>
<figure class="highlight http"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br></pre></td><td class="code"><pre><span class="line">POST https://api.stripe.com/v1/payment_intents/&#123;pi_id&#125;/verify_challenge</span><br><span class="line"></span><br><span class="line">captcha_response = &#123;hcaptcha_token&#125;     # P0开头的长字符串</span><br><span class="line">captcha_vendor_name = hcaptcha           # 固定值</span><br><span class="line">captcha_sitekey = xxxxxxxx-xxxx-xxxx    # Stripe 的 hCaptcha sitekey</span><br><span class="line">expected_amount = 98214                  # 交易金额</span><br><span class="line">expected_currency = php                  # 币种</span><br><span class="line">key = pk_live_xxx                        # Publishable Key</span><br><span class="line">_stripe_version = 2025-03-31.basil; checkout_server_update_beta=v1; ...</span><br><span class="line">client_secret = pi_xxx_secret_xxx        # PI 的 client_secret</span><br></pre></td></tr></table></figure>
<p>注意：</p>
<ul>
<li>字段名是 <code>captcha_response</code> 而不是 <code>challenge_response</code></li>
<li>需要同时传 <code>captcha_vendor_name</code> 和 <code>captcha_sitekey</code></li>
<li>需要传 <code>expected_amount</code>/<code>expected_currency</code> 做一致性校验</li>
<li>使用<strong>长版本</strong> <code>_stripe_version</code>（与 Hosted 模式一致）</li>
</ul>
<h3 id="5-3-hCaptcha-Enterprise-的特殊性">5.3 hCaptcha Enterprise 的特殊性</h3>
<p>Stripe 使用的不是普通 hCaptcha，而是 <strong>hCaptcha Enterprise</strong>。区别：</p>
<ol>
<li><strong>有 <code>rqdata</code> 参数</strong>：普通 hCaptcha 不需要 rqdata，Enterprise 必须传</li>
<li><strong>sitekey 是 Stripe 专有的</strong>：从 <code>elements/sessions</code> 响应的 <code>passive_captcha</code> 字段中提取</li>
<li><strong>invisible 模式</strong>：浏览器里看不到验证码图片，但后台在做风控评估</li>
</ol>

<h3 id="5-4-时效性问题">5.4 时效性问题</h3>
<p><strong>hCaptcha token 有时效性</strong>——浏览器里 ~4 秒解出即有效，但远程打码服务可能需要 30-120 秒。如果超时：</p>
<ul>
<li><code>verify_challenge</code> 返回 <code>payment_intent_authentication_failure</code></li>
<li>但 PI 状态仍然是 <code>requires_action</code>——<strong>可以重新 verify_challenge</strong></li>
</ul>
<p>解决方案分级：</p>
<ol>
<li><strong>最优</strong>：本地 headless 浏览器解 hCaptcha（&lt;5s，成功率 95%+）</li>
<li><strong>次优</strong>：支持 Enterprise rqdata 的快速打码 API（如 YesCaptcha，~15s）</li>
<li><strong>兜底</strong>：如果 PI 已经进入 <code>requires_action</code>，可以循环重试 verify_challenge（每次用新 captcha token）</li>
</ol>
<h3 id="5-5-3DS-vs-hCaptcha-的区别">5.5 3DS vs hCaptcha 的区别</h3>
<p><strong>重要澄清</strong>：Stripe 的 <code>verify_with_challenge</code> 并非传统银行 3DS 验证（3D Secure）。它是 Stripe 自有的风控挑战，使用 hCaptcha 作为人机验证手段。</p>
<p>真正的银行 3DS（如 Visa Secure）会打开银行页面要求输入 OTP/密码，这个在纯协议支付中<strong>无法绕过</strong>——但使用虚拟信用卡（VCC）通常不会触发银行 3DS，只会触发 Stripe 自身的 hCaptcha challenge。</p>

<h2 id="八、代理池架构">八、代理池架构</h2>
<p>协议支付的另一个核心组件是代理池。Stripe 和平台都会检查请求的源 IP，用数据中心 IP 直连容易被标记。</p>
<h3 id="8-1-双代理池">8.1 双代理池</h3>
<p>最佳实践是使用两个独立的代理池：</p>
<ul>
<li><strong>平台代理池</strong>：用于访问 SaaS 平台的 API（需要与账号注册地匹配）</li>
<li><strong>Stripe 代理池</strong>：用于访问 Stripe API（需要住宅 IP，避免被 Radar 标记）</li>
</ul>
<h3 id="8-2-代理健康检查">8.2 代理健康检查</h3>

<h3 id="8-3-出口-IP-一致性">8.3 出口 IP 一致性</h3>
<p><strong>关键规则</strong>：创建 Checkout Session 和确认支付时，必须使用<strong>同一个出口 IP</strong>。Stripe 会比对两次请求的 IP，如果不一致会拒绝交易。</p>
<p>这意味着整个支付流程中的所有请求（从创建 session 到 confirm）必须绑定同一个代理出口。如果代理池做了负载均衡，需要在支付流程中&quot;钉住&quot;一个代理节点。</p>

<h3 id="8-5-代理故障降级">8.5 代理故障降级</h3>
<p>代理不可用时的处理策略：</p>
<figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br></pre></td><td class="code"><pre><span class="line"><span class="keyword">async</span> <span class="keyword">def</span> <span class="title function_">get_proxy_with_fallback</span>(<span class="params">pool, country</span>):</span><br><span class="line">    proxy = <span class="keyword">await</span> pool.acquire(country=country)</span><br><span class="line">    <span class="keyword">if</span> proxy:</span><br><span class="line">        <span class="keyword">return</span> proxy</span><br><span class="line">    <span class="comment"># 降级：尝试其他国家的代理</span></span><br><span class="line">    proxy = <span class="keyword">await</span> pool.acquire(country=<span class="string">&quot;US&quot;</span>)</span><br><span class="line">    <span class="keyword">if</span> proxy:</span><br><span class="line">        <span class="keyword">return</span> proxy</span><br><span class="line">    <span class="comment"># 最终降级：直连（仅限测试环境）</span></span><br><span class="line">    <span class="keyword">if</span> config.allow_direct:</span><br><span class="line">        <span class="keyword">return</span> <span class="literal">None</span></span><br><span class="line">    <span class="keyword">raise</span> NoProxyAvailableError()</span><br></pre></td></tr></table></figure>
<p><strong>注意</strong>：不要在生产环境用直连降级——数据中心 IP 直连 Stripe 几乎必被拒。</p>
<hr />
<h2 id="九、状态机设计">九、状态机设计</h2>
<p>完整的协议支付需要处理多种失败场景和重试逻辑。最佳实践是使用状态机：</p>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br></pre></td><td class="code"><pre><span class="line">初始化 → 刷新Session → 检查权限 → 获取定价 → 创建Checkout</span><br><span class="line">    ↓           ↓           ↓           ↓           ↓</span><br><span class="line">  失败→退出   失败→退出  已有订阅→跳过  失败→退出   失败→退出</span><br><span class="line">                                                    ↓</span><br><span class="line">                                              更新税务 → 创建Token → 确认支付</span><br><span class="line">                                                ↓           ↓           ↓</span><br><span class="line">                                              失败→退出   卡被拒→换卡   3DS→验证</span><br><span class="line">                                                                        ↓</span><br><span class="line">                                                                    成功 / 失败</span><br></pre></td></tr></table></figure>
<p>每个状态转移都需要处理：</p>
<ul>
<li><strong>卡被拒（Card Declined）</strong>：分类拒绝原因（余额不足/CVV错误/风控拒绝），决定是换卡重试还是放弃</li>
<li><strong>3DS 验证</strong>：进入 Challenge 流程</li>
<li><strong>Session 过期</strong>：创建新 Session 重试</li>
<li><strong>Rate Limiting</strong>：TLS 指纹轮换 + 退避重试</li>
</ul>
<h3 id="9-1-Decline-错误分类">9.1 Decline 错误分类</h3>
<p>Stripe 的卡拒绝错误不是一个笼统的&quot;失败&quot;，而是分为可重试和不可重试两类：</p>
<p><strong>可重试（换卡后重试）</strong>：</p>
<ul>
<li><code>generic_decline</code> — 最常见，通常是风控拒绝，换卡几乎总能过</li>
<li><code>insufficient_funds</code> — 余额不足，充值后或换卡可过</li>
<li><code>processing_error</code> — Stripe 侧临时错误，直接重试</li>
</ul>
<p><strong>不可重试（放弃本次 session）</strong>：</p>
<ul>
<li><code>stolen_card</code> / <code>lost_card</code> — 卡已被标记，不能再用</li>
<li><code>card_not_supported</code> — 卡类型不支持（如某些预付卡）</li>
<li><code>currency_not_supported</code> — 卡不支持目标币种</li>
</ul>
<p><strong>需要特殊处理</strong>：</p>
<ul>
<li><code>incorrect_cvc</code> — CVC 错误，检查是否传错了</li>
<li><code>expired_card</code> — 卡过期，需要从卡池中移除</li>
<li><code>card_velocity_exceeded</code> — 卡的交易频率超限，冷却后可重试</li>
</ul>
<h3 id="9-2-Fast-Path-优化">9.2 Fast-Path 优化</h3>
<p>一个重要的状态机优化：<strong>如果 PI 已经 <code>succeeded</code>，跳过 hCaptcha</strong>。</p>
<p>HAR 中发现，有时 confirm 返回 <code>requires_action</code>（hCaptcha challenge），但 PI 实际上已经扣款成功。这时如果盲目去解 captcha，反而可能出错。</p>
<p>正确做法是在收到 <code>requires_action</code> 后，<strong>先查询 PI 状态</strong>：</p>
<figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br></pre></td><td class="code"><pre><span class="line">pi = stripe.get(<span class="string">f&quot;/v1/payment_intents/<span class="subst">&#123;pi_id&#125;</span>&quot;</span>, key=pk_live)</span><br><span class="line"><span class="keyword">if</span> pi[<span class="string">&quot;status&quot;</span>] == <span class="string">&quot;succeeded&quot;</span>:</span><br><span class="line">    <span class="comment"># 已经扣款成功，跳过 captcha</span></span><br><span class="line">    <span class="keyword">return</span> PaymentResult.SUCCESS</span><br><span class="line"><span class="keyword">elif</span> pi[<span class="string">&quot;status&quot;</span>] == <span class="string">&quot;requires_action&quot;</span>:</span><br><span class="line">    <span class="comment"># 确实需要解 captcha</span></span><br><span class="line">    solve_hcaptcha(pi)</span><br></pre></td></tr></table></figure>
<h3 id="9-3-Hosted-模式轮询">9.3 Hosted 模式轮询</h3>
<p>cs_live_ 模式在 confirm 之后需要轮询 <code>payment_page</code> 状态：</p>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br></pre></td><td class="code"><pre><span class="line">POST https://api.stripe.com/v1/payment_pages/&#123;cs_live_xxx&#125;/poll</span><br><span class="line">→ &#123;&quot;payment_intent&quot;: &quot;pi_xxx&quot;, &quot;status&quot;: &quot;open&quot;&#125;  // 等待中</span><br><span class="line">→ &#123;&quot;payment_intent&quot;: &quot;pi_xxx&quot;, &quot;payment_object_status&quot;: &quot;requires_action&quot;&#125;  // 需要 captcha</span><br><span class="line">→ &#123;&quot;payment_intent&quot;: &quot;pi_xxx&quot;, &quot;payment_object_status&quot;: &quot;succeeded&quot;&#125;  // 完成</span><br></pre></td></tr></table></figure>
<p>轮询间隔建议 2-3 秒，最多轮询 60 秒。如果超时未变化，检查是否需要手动 approve。</p>
<hr />
<h2 id="十、安全边界与最佳实践">十、安全边界与最佳实践</h2>
<h3 id="10-1-Session-隔离">10.1 Session 隔离</h3>
<p>每次支付使用独立的 Session，不复用已失败的 Session。特别是 Hosted 模式下，<code>approve</code> 操作后的 Session 不可再次使用。</p>
<h3 id="10-2-Dry-Run-模式">10.2 Dry-Run 模式</h3>
<p>所有实现都应支持 Dry-Run 模式——执行完整流程但不提交最终的 <code>confirm</code>：</p>
<figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br></pre></td><td class="code"><pre><span class="line"><span class="keyword">if</span> config.commit_payments:</span><br><span class="line">    result = stripe.confirm_payment_intent(pi_id, token)</span><br><span class="line"><span class="keyword">else</span>:</span><br><span class="line">    logger.info(<span class="string">&quot;Dry-run: skipping confirm&quot;</span>)</span><br></pre></td></tr></table></figure>
<p>这对于调试非常重要：你可以验证整个流程（创建 session、生成 token、税务计算）都正确，而不实际扣钱。</p>
<h3 id="10-3-不要存储敏感数据">10.3 不要存储敏感数据</h3>
<ul>
<li>信用卡号仅在内存中使用，支付完成后立即清除</li>
<li>Session token 不应写入日志（log 中用 <code>***</code> 替代）</li>
<li>代理凭据不要硬编码，用环境变量或加密存储</li>
<li>Stripe Publishable Key 可以写入代码（它本来就是公开的），但 Secret Key 绝不能出现在客户端</li>
</ul>
<h3 id="10-4-请求节奏模拟">10.4 请求节奏模拟</h3>
<p>纯协议支付的一个风险是请求速度<strong>太快</strong>。浏览器用户从打开支付页面到点击确认，通常需要 15-60 秒。如果你的自动化在 2 秒内完成全部请求，Stripe Radar 可能标记为异常。</p>
<p>建议在关键步骤间加入随机延迟：</p>
<figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br></pre></td><td class="code"><pre><span class="line"><span class="keyword">await</span> sleep(random.uniform(<span class="number">1.5</span>, <span class="number">3.0</span>))   <span class="comment"># 创建 session 后</span></span><br><span class="line"><span class="keyword">await</span> sleep(random.uniform(<span class="number">0.8</span>, <span class="number">2.0</span>))   <span class="comment"># 更新税务后</span></span><br><span class="line"><span class="keyword">await</span> sleep(random.uniform(<span class="number">1.0</span>, <span class="number">2.5</span>))   <span class="comment"># 创建 token 后</span></span><br><span class="line"><span class="keyword">await</span> sleep(random.uniform(<span class="number">0.5</span>, <span class="number">1.5</span>))   <span class="comment"># confirm 前</span></span><br></pre></td></tr></table></figure>
<p>总时间控制在 8-30 秒之间比较自然。</p>
<h3 id="10-5-并发控制">10.5 并发控制</h3>
<p>批量处理多个账号时，不要让所有请求同时发出：</p>
<ul>
<li><strong>Stripe API</strong>：有 rate limit，同一 publishable key 下大量并发 confirm 会触发 429</li>
<li><strong>平台 API</strong>：多个账号同时操作可能触发风控</li>
<li><strong>代理池</strong>：每个代理 IP 上同时只运行 1-2 个支付流程</li>
</ul>
<p>建议使用信号量（semaphore）限制并发：</p>
<figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br></pre></td><td class="code"><pre><span class="line">sem = asyncio.Semaphore(<span class="number">3</span>)  <span class="comment"># 最多同时处理 3 个支付</span></span><br><span class="line"><span class="keyword">async</span> <span class="keyword">with</span> sem:</span><br><span class="line">    <span class="keyword">await</span> process_payment(account)</span><br></pre></td></tr></table></figure>
